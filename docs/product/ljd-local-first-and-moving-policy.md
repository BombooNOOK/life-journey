# Life Journey Diary｜Local-first・森のお引越し便 基本方針

**Status:** Current Pre-Hybrid Data Architecture Policy / Source of Truth  
**適用:** Hybrid版のデータ所有・保存・オフライン・機種変更・お引越し設計  
**関連:** `ljd-product-worldview-source-of-truth.md`（世界観）／`ljd-account-resident-terminology-spec.md`（用語）／`ljd-acorn-monetization-spec.md`（どんぐり）

### 記載のラベル

- **FACT:** 現行コード・リポジトリ実測・公式一次資料から確認できる事実
- **OS仕様:** Apple / Google / Capacitor 公式に基づく一般仕様（LJD未実装のもの含む）
- **製品判断:** 本PhaseでLJDとして採用する方針（未実装可）

## 1. 要約（製品判断）

1. Hybrid版 LJD は **Local-first / Device-first** を基本とする。  
   人生記録の**主保存先は本人の端末**であり、サーバーへのキャッシュ複製ではない。
2. データ保護は二段構えとする。  
   - **第一防衛線:** OS標準のお引越しを活かせる永続保存配置  
   - **第二防衛線:** **森のお引越し便**（あしあと小包）をユーザー自身の Drive / Files / PC 等へ  
3. **森のお預かり棚**（運営クラウドでの大容量人生記録預かり）は初期 Hybrid の必須機能としない。  
4. 「OS標準移行だから必ず全部移る」ことを **LJDとしては保証しない**。  
5. 現行Webの Neon / Vercel Blob 中心構造は **移行元（現状）** であり、Hybrid最終構造ではない。

標語（世界観SoTと同一）:

> 端末は変わっても、森はそのまま。  
> 人生の記録は、まず本人の手元にある。  
> （長期）運営が変わっても、あなたのあしあとはあなたのもの。

## 3. Hybrid版の目標構造（製品判断）

### 3.1 二分類

| 分類 | 意味 |
| --- | --- |
| **device-primary** | 人生記録の原本。端末の永続領域が正。通信なしで読み返し・（候補として）新規あしあと作成が可能になるよう設計する |
| **server-primary** | サービス運営に必要な情報。サーバーが正。端末は必要に応じ参照・キャッシュ |

### 3.2 推奨配置（Hybrid目標）

```
[本人の端末 = 原本]
  Documents / Application Support 相当（バックアップ対象・Cache以外）
    ├─ あしあと本文・写真・下書き・タグ等
    ├─ 森ログ完成カード／ムービー／映写／下書き
    ├─ アルバム構成・caption
    └─ （候補）お庭などの長期人生状態

[ユーザー自身のクラウド／Files／PC]
  └─ あしあと小包（森のお引越し便）… 第二防衛線

[LJDサーバー]
  ├─ 認証・住民識別・不正防止
  ├─ どんぐり台帳・購入決済・製本注文
  ├─ 運営ポスト／問い合わせ
  └─ （移行期間）Web時代データの配信元 ※削除タイミングは未決
```

単に「WebViewの IndexedDB を増やす」方針は採用しない（§8）。

## 4. device-primary にするデータ

### 4.1 第一候補（製品判断・採用）

| データ | 理由 |
| --- | --- |
| あしあと本文 | 人生記録の中核。手元所有の中心 |
| あしあと写真（長期保存すべき表示用） | 思い出の実体。サーバー恒久保管を前提にしない |
| あしあと下書き | 通信断でも書き途中を守るため |
| タグ・整理情報（あしあと／ブックに属するもの） | 本人の整理の一部 |
| 森ログカード／ムービー／映写完成品 | 「再会」体験の中核。現状最も消失リスクが高い |
| 映写下書き | 大容量だが制作途中の本人資産 |
| アルバム構成・並び・カバー | 完成メディアとセットで意味を持つ |
| caption 等の付随情報 | メディアメタと不可分 |
| その他、ユーザーが長期保存すべき人生記録（後述お庭など） | 世界観上「森に残したもの」 |

### 4.2 除外提案（デバイス原本にしにくい／しなくてよい）

| データ | 提案 | 理由 |
| --- | --- | --- |
| SNS投稿用生成画像 | device-primaryの必須から除外可 | オンデマンド再生成可能（FACT: 合成API／端末一時）。調整値のみローカルに残り得る |
| アプリ同梱BGM・テンプレ素材 | ユーザー原本にしない | バンドル資産 |
| 鑑定フルPDF（高画質製本相当） | お引越し便へ**無条件同梱しない**（§6） | 再生成可能な巨大派生物。Order入力＋稿があれば再出力できる設計を優先 |
| Firebaseセッション本体 | 引越し対象外 | 再認証で再構築 |
| UI tips・一回限りフラグ | 任意。消失許容 | 人生記録ではない |
| 運営admin下書き | 対象外 | 運営データ |

### 4.3 お庭（提案）

現行は Neon（FACT）。製品判断では **device-primary 候補**（森に育つ状態＝人生に近い体験状態）。  
初期Hybridで庭まで含むかは **未決（実装優先度）**。方針上は「人生側」に寄せる。

## 5. server-primary に残すデータ（項目ごと理由）

「今サーバーにあるから」ではなく、**なぜサーバーが正である必要があるか**。

| データ | サーバーに置く理由（製品判断） |
| --- | --- |
| Firebase認証 | 本人証明・セッション発行。端末だけではアカウント復旧・不正防止が成立しない |
| アカウント識別（email等） | サービス契約・問い合わせ・課金主体 |
| 森の住民番号・発番 | 運営照合・問い合わせの不変ID。端末のみだと紛失時に照合不能 |
| どんぐり残高／台帳 | 経済・消費の改ざん耐性。複数端末で矛盾させないため正はサーバー |
| 購入・決済（Stripe等） | 法務・領収・チャージバック。端末原本にできない |
| 製本注文・進捗 | 外部制作フローと状態共有が必要 |
| 運営ポスト／お知らせ配信元 | 運営が発信し、到達を保証する側がサーバー |
| 既読状態 | 配信側との整合（端末キャッシュは可）。サーバー正を推奨 |
| 問い合わせスレッド | 運営対応の正本 |
| 管理者フラグ等 | 権限はサーバー検証必須 |
| 不正防止に必要なログ／制限 | クライアント信頼不可 |
| 課金状態のサーバー側記録 | 権利付与の根拠 |
| （移行期間）Web時代のあしあと／写真配信 | Hybrid未移行ユーザーと共存のため。**恒久原本としては最終的に端末へ**（削除時期は未決） |

読書フォントサイズ等の軽微設定: server同期は現行Web便宜（FACT）。Hybridでは **device-primaryでも可**。serverに残す必然は弱い（未決だが方針上は端末でもよい）。

## 6. 鑑定の分類とPDF容量

### 6.1 分離（製品判断）

| 層 | 内容 | 原本候補 |
| --- | --- | --- |
| 入力人物情報 | 名アクセント・生年月日等 | サービス注文としては server；ユーザー手元コピーは device 可 |
| numerology計算結果 | `numerologyJson` 等 | 入力＋計算ロジックから再導出可能な場合あり。保存は「入力＋結果キャッシュ」 |
| 読み解きデータ | 本文データ／参照キー | 再生成方針とセットで設計 |
| 鑑定PDF | レンダリング成果物 | **派生物** |
| 製本用情報 | 申込・配送・プラン | **server-primary** |

### 6.2 PDFを無条件にお引越し便へ入れるか

**製品判断:** 入れないことを第一候補とする。

理由:

1. 派生物であり、入力と生成パイプラインがあれば再出力できる（設計目標）。
2. 容量が大きく、小包・OSバックアップを圧迫する。
3. 「人生の記録の手元所有」は、**あしあと／森ログ**の方が優先度が高い。

必要なら「手元で読みたい」用途の**任意エクスポート**（人間可読）として将来の長期保存用機能に寄せる。

### 6.3 実容量調査（FACT・推測禁止）

本番 Neon 上の実注文PDFバイト数は、本作業環境から本番DBを読んでいないため**未取得**。以下はリポジトリ内で確認できた事実。

| 観測 | 値 | 根拠 |
| --- | --- | --- |
| `sample-booklet-low.pdf`（リポジトリ同梱サンプル） | **約 10.46 MiB** | ファイル実測 `sample-booklet-low.pdf` |
| 同PDFのページ痕跡（粗計） | `/Type /Page` 出現 **約67** | バイト列カウント（厳密な pdf page tree ではない） |
| 鑑定PDF用ローカル素材一式 | **約 126 MiB**（フォント＋画像等103ファイル） | `src/components/pdf/assets` 合計 |
| うち大きい全面PNG例 | introduction-page-2.png **約4.08 MiB** 等 | 個別実測 |
| 現行あしあとZIP上限 | **100 MiB**／entry・photo 各2000 | `JOURNAL_BACKUP_MAX_ZIP_BYTES` 等（FACT） |
| 映写ソース動画上限 | **200 MiB**／長さ最大60秒 | `MORI_LOG_DEVICE_MOVIE_MAX_SOURCE_BYTES`（FACT） |
| プレビュー／製本PDF | Blobに `preview` と `print`（high）を分けてキャッシュ | `orderPdfBlobCache.ts`（FACT）。個別バイト未計測 |

**含意（製品判断）:** 低画質サンプルでも約10MiB級。製本相当・フル冊子を複数手元保管すると、あしあと小包やOSバックアップ枠を圧迫しうる。よってPDF無条件同梱は非推奨。本番実測（代表Orderの preview/print 各サイズ）は Phase 2前に別タスクで行うこと（未決計測）。

## 7. オフライン要件（製品判断）

### 7.1 通信なしで成立させたいこと（Hybrid目標）

- 過去のあしあとを読む
- 保存写真を見る
- 森ログを見る
- アルバムを見る
- 過去の自分の記録を振り返る（本棚メタのローカル保持含む）

### 7.2 実現候補

- **新しいあしあとをオフラインで残す**（端末キュー。オンライン復帰後に、どんぐり消費等のサーバー処理と整合）

オフライン新規作成時のどんぐり整合は **未決**（先行して端末に書き、復帰時に台帳確定／不足時の扱いを要設計）。

### 7.3 オンライン必須（明示）

| 機能 | 理由 |
| --- | --- |
| 新しいオンライン鑑定処理 | 計算・保存・注文フローがサーバー／課金と結合 |
| 購入・決済 | 外部決済 |
| どんぐり獲得・消費の確定 | server-primary台帳 |
| 運営ポストの新規取得 | 配信元がサーバー |
| 製本申込 | 運営フロー |
| （初期）サーバー→端末の初回移行ダウンロード | 移行専用 |

閲覧系の鑑定PDFは「キャッシュがあればオフライン可／なければオンライン再生成」が現実的（未決詳細）。

## 8. OS標準移行（第一防衛線）

### 8.1 位置づけ（製品判断）

最大限利用する。ただし **保証しない**。ユーザーへの説明も「できるだけ助かる／保険ではない」とする。

### 8.2 iOS（OS仕様・公式）

出典例:

- Apple「Using the file system effectively」／File System Basics  
  - **Documents**・**Application Support**: バックアップ対象（iCloud / コンピュータバックアップ）  
  - **Caches**: バックアップ対象外。容量逼迫時に破棄され得る  
  - `isExcludedFromBackupKey` で個別除外可  
- WebKit: localStorage 等を backup から除外する経緯あり（iCloudバックアップに載せない方針の歴史）。**WKWebView の website data（IndexedDB含む）に人生原本を置き続けることは、機種変更保証の根拠にならない**（製品判断）。

**LJD含意:** 人生原本は Filesystem の永続ディレクトリへ。Cache／純粋WebViewストレージ依存を避ける。

### 8.3 Android（OS仕様・公式）

出典: Android Developers「Auto Backup」「Data backup overview」

- Auto Backup は `getFilesDir` / DB / SharedPreferences / 外部app files 等を含む一方、**cache / no_backup は除外**
- **クラウド Auto Backup はアプリあたりおおよそ 25 MB 上限**（公式概要）。大容量あしあと写真・動画はクラウド自動バックアップだけでは足りない可能性が高い
- Device-to-device (D2D) 転送は別トランスポート。クラウド上限と挙動が異なるが、**「必ず全部」保証はできない**（製品判断）

**LJD含意:** 大容量はあしあと小包（ユーザー自身の Drive）が実質必須。Auto Backupだけに依存しない。

### 8.4 Capacitor（OS仕様・公式 docs）

出典: Capacitor Filesystem / Preferences 公式API

| API | 向き |
| --- | --- |
| **Filesystem `Directory.Data`** | アプリ私有。**注意: 公式どおり iOSでは Documents を使用**し、Androidは app files。アンインストールで消える |
| **Filesystem `Directory.Library`** | iOS Library（Application Support寄り）。Androidは app files |
| **Filesystem `Directory.Cache`** | 破棄され得る。人生原本禁止 |
| **Filesystem `Directory.Documents`** | iOSアプリDocuments。AndroidはPublic Documents系で挙動差大（Android 11+制約） |
| **Preferences** | 軽量KV。UserDefaults / SharedPreferences。**大量・複雑クエリ向きではない**（公式注意）。OSが `localStorage` を消す可能性への代替、と明記 |

**旧Hybrid branch FACT:** `origin/feature/hybrid-v0.1-capacitor` は App/Keyboard/StatusBar 殻。Preferences/Filesystem 未導入。オフライン保存は v0.2+ と文書化。

### 8.5 Hybrid保存への推奨（製品判断・未実装）

| データ種別 | 推奨領域 |
| --- | --- |
| あしあとDB・写真・森ログ完成メディア | iOS: Application Support 相当（ユーザーに生ファイルを晒さない）またはDocuments（「見える人生ファイル」方針なら）。Android: `getFilesDir` 相当（Auto Backup／D2D対象側）。**Cache禁止** |
| 軽い設定フラグ | Preferences |
| 再取得可能なキャッシュ | Cache または `isExcludedFromBackup` |

大容量動画: OSバックアップ肥大化に注意。必要ならバックアップ除外＋あしあと小包必須、の組み合わせを Phase 2で検討（未決）。

## 9. 森のお引越し便（第二防衛線）

### 9.1 UX（製品判断）

技術語（export/import/upload/download）を前面に出さない。

旧端末: **森のお引越し便をつくる** → LJDが必要データをまとめる → **保存先を選ぶ** → iCloud Drive / Google Drive / Files / PC 等  
新端末: **森のお引越し便を受け取る** → 小包を選ぶ → LJDが復元

### 9.2 あしあと小包

ユーザーからは**一つの小包**に見えることを第一候補とする。  
内部名例: `LifeJourneyDiary-Move-YYYYMMDD`（未確定）。  
ユーザー向け名称候補: **あしあと小包**（用語確定はコピー工程。terminology との整合を取る）。

ZIP拡張子を変えるだけでは安全にならない。Phase 2で設計する項目（本Phaseは列挙のみ）:

- package manifest / schema version  
- ファイル整合性・checksum・破損検出  
- 暗号化  
- 復元可能性・将来バージョン互換  
- 大容量動画の分割／参照  
- 中断時の安全性・restore原子性  
- 重複処理・同一住民判定  

### 9.3 定期的な小包作成案内（製品判断）

端末故障・水没では「直前に作る」暇がない。将来:

- 最後に小包を作った日  
- それ以降の増分データ量  
- 一定期間経過  

などを使い、**穏やかな案内**のみ。強制・不安煽りUIは禁止（世界観SoT）。

## 10. 現行「あしあとのバックアップ」との関係

### 10.1 現行位置づけ（FACT + 用語SoT）

- もしもの保険としてあしあと本文・写真等を手元に残す  
- 森ログ等は含まない  
- 非暗号化ZIP（現行実装事実 ≠ 最終仕様）  
- 「森のお引越し」は用語SoT上、**別機能として検討**と既記  
- ユーザー自己restore未実装。運営は新規Profile復元

### 10.2 比較（製品判断・統合はしない）

| 案 | 内容 | 評価 |
| --- | --- | --- |
| **A 別機能として残す** | 保険ZIPとお引越し便を並存 | 現用語・現ユーザー理解と最も整合。移行期安全 |
| **B 同一基盤・用途分岐** | 1つのパッケージエンジン、UIは保険／お引越しで差 | 中長期で自然。実装コスト中 |
| **C お引越しへ統合** | バックアップを廃止または吸収 | 破壊的。現段階では不採用 |

**現時点の推奨:** **Aを当面維持**し、設計としては **Bを将来の統合形として視野に入れる**。Cはしない。  
本Phaseで機能を統合しない（依頼どおり）。

## 12. 「運営が潰れても手元に」と可読長期保存

思想は世界観SoTに記す。

お引越し便が LJD専用形式のみだと、将来アプリが動かなくなったときに読めないリスクがある。  
よって将来課題として、**人間可読な長期保存用書き出し**（テキスト／写真／PDF／HTML等）を別機能候補に記録する。本Phaseでは実装しない。

## 13. 既存Webユーザーの端末原本化（設計論点）

想定フロー（例）:

サーバー（Neon/Blob）→ 初回Hybridログイン → 端末へ完全取得 → 整合性検証 → Local原本化

### 別論点（未決・削除時期は決めない）

| 論点 | 内容 |
| --- | --- |
| 移行確認 | 件数・バイト・checksum・写真欠損検査 |
| rollback | 端末化失敗時にサーバー正へ戻せるか |
| 移行失敗 | 再試行、部分移行、ユーザー通知（穏やか） |
| 複数端末 | 二台同時に「原本」を主張した場合（§14） |
| 同期競合 | Local-firstでは自動マルチ同期を前提にしない |
| サーバー削除タイミング | **本Phaseで決めない** |
| Web共存期間 | Hybrid公開後もWebが残るなら、二重原本禁止ルールが必要 |

## 14. 複数端末問題

Local-first ≠ 複数端末自動同期。

| 選択肢 | 概要 | 向き |
| --- | --- | --- |
| 1 primary device | 正は1台。他は読み取りまたはお引越しで継ぐ | 初期Hybridと相性良い |
| ユーザー自身のiCloud等 | OS／ユーザーDriveに任せる | LJDが同期サーバを持たない方針と整合 |
| お引越し方式のみ | 手動で森を運ぶ | シンプルだが手間 |
| 将来sync | 運営または専用同期 | 預かり棚に近いコスト。後回し |

**初期推奨（製品判断）:** **1 primary device** ＋ 第二防衛線（小包）＋ OSバックアップ。マルチ同期は将来検討。

## 15. セキュリティ論点（方針）

| 論点 | 方針メモ |
| --- | --- |
| 小包の暗号化 | Phase 2で必須検討。現行あしあとZIPは非暗号化（FACT） |
| 端末紛失 | OSのFile Protection／端末ロックに依存。端末原本化は「手元」と同時に紛失リスクも本人側へ移る |
| 小包をDriveに置く | ユーザー所有クラウドの権限・共有ミスに注意。説明コピーが必要 |
| 改ざん | checksum／署名。どんぐり台帳はサーバー検証を維持 |
| WebViewストレージ | 人生原本に使わない |

## 16. 初期Hybridで「お預かり棚なし」で成立するか

**成立する（製品判断）。** 条件:

1. device-primary を OSバックアップ対象領域へ置く  
2. あしあと小包（森ログ含む）を第二防衛線として提供  
3. サーバーは認証・どんぐり・商業・運営情報に限定  
4. 既存ユーザー移行パスを公開前に設計する  

条件が欠けると「端末は変わっても森はそのまま」は守れない。
